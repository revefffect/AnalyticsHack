## Задача

Сотрудник ведёт наблюдения в урочище «Красное» и сейчас готовит сводки вручную в Excel. В приложении он выбирает станцию, показатель и период, получает таблицу и график с единицами, проверяет пригодность ряда и по необходимости открывает исходные строки. Сотрудник, который ведёт архив, может зарегистрировать новую точку, проверить выгрузку перед сохранением и позднее пополнить историю станции.

Задание опирается на `case-2-weather.pdf`, «Хакатон ПФП — критерии оценки проектов» и документацию в `meteo_hack_dataset.zip`. В архиве 35 CSV наблюдений и `coverage_by_month.csv`. Наборы передаются приложению из локального каталога. Адрес каталога задаётся при запуске. Архив хранится отдельно от Git.

В исходном кейсе наблюдения передаются как CSV. Портал также принимает Excel и JSON с массивом записей или полем `records`. Форматы используют общую нормализацию и правила.

## Правила данных и расчёта

- Начальные станции — АМЕ‑60 (1992–2021), Сокол М1 Кр1 «Поляна» и Кр2 «Поле» (2022–2025). У каждой точки самостоятельная история. Архивные ряды АМЕ‑60 и Сокол М1 отображаются отдельно, в том числе при построении трендов.
- Храним время замера как в файле. Часовой пояс архива неизвестен. Часовые группы используются для проверки полноты и для суточного хода. Расчёт ведётся по календарю источника.
- `dup_conflict` исключает исходную строку целиком. Флаг `параметр:причина` исключает только значение соответствующего параметра. Пустые и исключённые значения остаются доступны в деталях с соответствующим статусом. Различаем отсутствующий столбец, неполный период и сомнительное значение.
- Для АМЕ‑60 нужны минимум 72 уникальных срока из 96 за сутки, для Сокол М1 — минимум 18 различных часов из 24. Суточное среднее — арифметическое среднее всех пригодных значений показателя за день. Записи в одном часу имеют одинаковый вес с другими пригодными записями при расчёте суточного среднего.
- Месяц проходит при не более 10 неполных днях и максимальной серии неполных дней до 4 включительно. Проверяется весь календарный месяц, включая дни без записей и 29 февраля. Для неполного интервала по фильтру показываем фактические границы и явно отмечаем частичный период. Декады — 1–10, 11–20 и 21-е число — конец месяца.
- Покрытие станции сверяется с `coverage_by_month.csv`. Покрытие показателя вычисляется отдельно по пригодным значениям. Для давления Кр1 за 2024 год оно определяет допустимость суточных и месячных сводок. Правило давления применяется только к нему. Для остальных показателей итоговые правила и исключения нужно зафиксировать в методике до реализации, отдельно от общего покрытия.
- Для скалярных показателей предлагается агрегировать декадные и месячные средние по пригодным суточным средним с одинаковым весом дней. Для исторического ориентира сравнивать сопоставимые календарные периоды, показывать «среднее за выбранный период», годы и число лет. Для направления ветра использовать круговое представление или частоты по секторам. Направление у АМЕ‑60 отсутствует в 1998 году и недостоверно за весь 2021 год.
- Для сравнения Кр2 − Кр1 месячная разница считается по общим пригодным календарным дням. Для суточного хода усредняем записи каждой станции в одном и том же дне и часу, вычитаем одно среднее из другого, затем усредняем разницы по датам для каждого часа. Показать количество пар. Время подписывать как время архива.

## Проверка на архиве

Для воспроизведения используйте Python 3.12 или новее. Скрипт читает исходный ZIP, печатает независимую сверку покрытия и значения для защиты.

```bash
python3 scripts/audit_archive.py '/path/to/meteo_hack_dataset.zip'
```

| Случай | Ожидаемое значение |
|---|---|
| Исходный архив | 874 560 строк наблюдений. Покрытие совпадает для всех 420 строк `coverage_by_month.csv` |
| АМЕ‑60, 1 июля 1993 | 96 пригодных замеров температуры воздуха, среднее 12,502083… °C |
| Кр1, апрель 2024 | 28 пригодных дней по станции, 2 по давлению. Месяц проходит по станции, давление исключается из месячной сводки |
| Кр1, давление за 2024 | 334 пригодных дня, 11 пригодных месяцев |
| Регистрация Кр2 из `kr2_2024.csv` | 17 300 строк, 366 пригодных суток по температуре, 12 пригодных месяцев |
| Пополнение Кр2 через `kr2_2025.csv` | 11 992 новых строки, 29 292 строки суммарно. Повторный импорт каждого файла сохраняет те же счётчики |

## Техническое решение

Портал использует **Python 3.12, Django 5.2 LTS, SQLite и Docker Compose**. MapLibre рисует карту каталога, ECharts строит отчёт и показывает пригодность измерений. Superset читает выбранные архивные срезы из DuckDB. Grafana и InfluxDB обслуживают входящие потоки и архивные агрегаты. Plotly используется в ноутбуке и деталях потока.

Импорт и контроль качества, расчёт метрик и интерфейс имеют отдельные зоны ответственности. Интерфейс использует ту же реализацию расчётов, что CLI и тесты. Модель хранит станцию, версию профиля, пакет импорта с контрольной суммой, исходное наблюдение, результат проверки и суточные сводки. Файл проверяется до сохранения. Импорт и обновление производных данных должны быть атомарны. Идентичные повторы учитываются один раз, конфликтующие версии исходных строк сохраняются для проверки. Ожидаемые запросы проверяются на полном архиве.

На первом релизе оператор может менять данные карточки станции и выбирать профиль подсчёта полноты. В сводке сотрудник настраивает диапазон дат, показатель, детализацию, периоды сравнения и исторического среднего и фильтр качества. Канонические правила кейса версионируются. Для новых типов станции профиль указывается явно. Изменение профиля должно быть прослеживаемым в истории расчётов. Фильтр качества меняет представление и оставляет методику сводки видимой.

## Критерии готовности

- Чистая установка из репозитория с фиксированными версиями зависимостей, миграциями, инструкциями для локального запуска и запуска в Yandex Cloud. Готовы действия импорта исходного ZIP, резервного копирования и восстановления, проверки здоровья приложения. Данные переживают перезапуск. Статические ресурсы доступны при локальном показе без сети.
- Проверены роли читателя и оператора импорта. Экран проверки объясняет ошибку файла или частичное покрытие. Подтверждение операции обновляет ровно одну станцию и выдерживает повтор или одновременную загрузку того же файла.
- `pytest` с `pytest-django` проверяет формулы, граничные случаи, загрузку через БД и CLI и эталоны полного архива локально. Минимум 90% покрытия ветвей для модулей импорта, флагов и агрегирования как стартовая цель. Критические случаи фиксируются отдельными проверками независимо от общего процента.
- Playwright проверяет переход от сводки к причине исключения и исходным данным, а также регистрацию станции, импорт, обновление и повторный импорт. Проверить также пустое состояние, ошибки формы, навигацию с клавиатуры и просмотр таблицы на узком экране.
- CI запускает форматирование и линтер в режиме проверки, тесты и браузерные сценарии на небольших тестовых данных. Перед сдачей отдельно прогнать полный архив, измерить время ответа и отрепетировать демонстрацию. Критические сценарии и измеренные результаты указать в итоговом README.

## Порядок реализации

1. Сформировать контракт расчётов и воспроизводимые эталоны, проверить границы окна и полноты.
2. Собрать сквозной путь от архива до первой сводки и объяснения качества. Сверить его с работой пользователя на одном задании.
3. Довести регистрацию и пополнение станции до обработки повторов, ошибок и восстановления. Добавить сравнение поля и поляны.
4. Пройти критерии выпуска и репетицию защиты по реальному архиву.
